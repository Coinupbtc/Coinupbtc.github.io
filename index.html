Data integrity

A backup that passed for 15 days while saving one file

Found
A nightly backup reported success for 15 days in a row. Each archive held 1 file instead of the full configuration set.
Root cause
The check confirmed the archive existed. It never looked inside.
Fix
Replaced presence checks with entry-count verification on every backup tier.
Lesson
The same failure as a calibration sticker that no longer matches its certificate: the indicator kept saying "good" after it stopped measuring anything.

Evidence My home lab. I’ll walk through it in an interview.

Metrics

A score that could not come out wrong

Found
A reporting tool’s headline accuracy metric could never come out wrong, and its results board included 118 of 144 events that had already finished.
Root cause
The baseline was derived from the same data it graded, so the metric agreed with itself by construction.
Fix
Rebuilt it with leave-one-out baselines and an independent scoring harness.
Verified
The metric can now fail, which is the only way a passing score means anything.

Evidence Private project. I’ll walk through it in an interview.

Release gate

A release gate that rejected the better build

Found
A fine-tuned AI model scored better on its target task but failed 4 unrelated checks: 15/19 on the release gate.
Rule
A build ships only at 19/19. No exceptions for a better headline number.
Fix
Rejected it and rebuilt the training set: 2,883 pairs generated by two independent models and graded on their agreement.
Verified
19/19 on the gate. On 104 held-out records: 96.2% field-level accuracy against 89.2% for the base model, and 71% fully correct against 34%.

Evidence The 19-check gate Training scripts

Performance

From 13 seconds to 7.5 milliseconds

Found
Selecting one row in a 516-record list took 13 seconds.
Root cause
Every filter pass rebuilt every row and parsed the same files again.
Fix
Stopped rebuilding rows that hadn’t changed and removed the repeated parsing.
Verified
A flat 7.5 ms, measured before and after.

Evidence The bug and the fix, timed in your browser

Study

Control charts against machine learning on real factory data

Question
Do machine-learning alarms catch failing production runs better than classic control charts?
Method
Public UCI SECOM data: 1,567 production runs, 590 sensors. Same 1% false-alarm budget for every method, tested on later runs only. I committed the analysis plan before scoring the test data.
Result
No method reliably beat chance. Control limits set on early runs over-alarmed 1.8–4.2× their 1% target on later runs.

Evidence Repo with plan, deviations log and results

How I work

Three rules I use on the floor and in code

Presence is not integrity

A file that exists, a 200 response, a sticker on a meter. None of them prove the contents are right, so I check the contents.

Baseline first

Record how a system behaves before changing it. Without a baseline, an improvement is just a claim.

One change at a time

Change one setting, measure again, and keep it only if the evidence says so.

The lab

Two AI machines at home, run like a test bench

Two NVIDIA DGX Spark computers with 121 GB of memory each run AI models locally. Nothing is rented in the cloud. I tune them the way I’d qualify equipment: record a baseline, change one thing, measure again.

Since June they’ve run Hermes Agent, Nous Research’s open-source AI agent, around the clock against a DeepSeek-V4.1 model split across both machines. Three of my fixes to that model’s serving engine are now upstream, including one that stops text in a fetched web page from posing as a command to the model.

Speed isn’t the test. Turning off the model’s step-by-step "thinking" made replies much faster, so I turned it off. A blind comparison on my own questions then preferred thinking on 8 times out of 9, and 9 of 10 on a re-test, so it’s back on.
